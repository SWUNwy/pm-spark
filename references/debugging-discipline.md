# 系统化调试（analyze 内部能力）

## 概述

随机修复浪费时间和制造新 bug。快速补丁掩盖根本问题。

**核心原则：先找到根因，再尝试修复。症状修复就是失败。**

**违反本流程的字面形式，就是违反调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

未完成第 1 阶段，就不能提议修复。

## 何时使用

任何技术问题都适用：
- 测试失败
- 生产 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其要使用：**
- 时间压力下（紧急情况让人想猜）
- "就快速修一下"看起来很显然时
- 已经试过多次修复时
- 之前的修复没生效时
- 还没完全理解问题时

**不要跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你赶时间（赶时间保证返工）
- 经理要 NOW 修好（系统化比乱撞更快）

## 四个阶段

进入下一阶段前必须完成上一阶段。

### 阶段 1：根因调查

**尝试任何修复之前：**

1. **仔细读错误消息**
   - 不要跳过错误或警告
   - 它们常含精确解法
   - 完整读堆栈
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 精确步骤是什么？
   - 每次都发生吗？
   - 不可复现 → 收集更多数据，不要猜

3. **检查最近改动**
   - 什么变化可能导致此问题？
   - Git diff、最近提交
   - 新依赖、配置变化
   - 环境差异

4. **多组件系统收集证据**

   **系统有多个组件时（CI → build → 签名，API → service → database）：**

   **提议修复前，先加诊断插桩：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层状态

   运行一次收集证据，显示它在哪里断
   然后分析证据，找出失败组件
   然后调查该组件
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示：** 哪层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **错误深在调用栈时：**

   完整后向追踪技术见本目录 `root-cause-tracing.md`。

   **快速版：**
   - 坏值从哪来？
   - 谁用坏值调用了这里？
   - 一直向上追踪直到找到源头
   - 修源头，不修症状

### 阶段 2：模式分析

**修复前先找模式：**

1. **找工作示例**
   - 在代码库中找相似的可用代码
   - 什么和坏掉的类似且能工作？

2. **对照参考**
   - 实现模式时，完整读参考实现
   - 不要略读——读每一行
   - 应用前完全理解模式

3. **识别差异**
   - 可用与坏掉之间的差异是什么？
   - 列出每个差异，无论多小
   - 不要假设"那不可能有关系"

4. **理解依赖**
   - 需要哪些其他组件？
   - 哪些设置、配置、环境？
   - 它做什么假设？

### 阶段 3：假设与测试

科学方法：

1. **形成单一假设**
   - 明确陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 具体，不要含糊

2. **最小化测试**
   - 做最小可能的改动来验证假设
   - 一次只变一个变量
   - 不要同时修多个东西

3. **继续前先验证**
   - 生效了？→ 阶段 4
   - 没生效？→ 形成新假设
   - 不要在上面叠加更多修复

4. **不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 求助
   - 继续研究

### 阶段 4：实施

**修根因，不修症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 尽量自动化测试
   - 没有框架就写一次性脚本
   - 修复前必须有

2. **实施单一修复**
   - 处理已识别的根因
   - 一次一个改动
   - 不做"顺手"改进
   - 不捆绑重构

3. **验证修复**
   - 测试现在通过？
   - 其他测试没坏？
   - 问题真正解决？

4. **修复无效时**
   - 停止
   - 数一下：已试几次修复？
   - < 3 次：回到阶段 1，用新信息重新分析
   - **≥ 3 次：停止并质疑架构（下方第 5 步）**
   - 未经架构讨论不要尝试第 4 个修复

5. **3+ 次修复失败：质疑架构**

   **指示架构问题的模式：**
   - 每个修复都在不同位置揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每个修复都在别处制造新症状

   **停止并质疑基本面：**
   - 这个模式根本上是健全的吗？
   - 我们是否只是"凭惯性坚持"？
   - 应该重构架构，还是继续修症状？

   **尝试更多修复前与人类伙伴讨论**

   这不是失败的假设——这是错误的架构。

## 红旗——停止并按流程走

如果你发现自己想：
- "先快速修，之后再调查"
- "就试试改 X 看行不行"
- "加多个改动，跑测试"
- "跳过测试，我手动验证"
- "大概是 X，让我修它"
- "我不完全理解但这可能有用"
- "模式说 X，但我换个方式改"
- "主要问题是：[列修复却无调查]"
- 未追踪数据流就提方案
- **"再试一次修复"（已试 2+ 次时）**
- **每个修复都在不同位置揭示新问题**

**这些都意味着：停止。回到阶段 1。**

**3+ 次修复失败：** 质疑架构（见阶段 4.5）

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|---|---|---|
| **1. 根因** | 读错误、复现、查改动、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找工作示例、对照比较 | 识别差异 |
| **3. 假设** | 形成理论、最小测试 | 确认或新假设 |
| **4. 实施** | 建测试、修复、验证 | bug 解决、测试通过 |

## 当流程揭示"无根因"

若系统化调查显示问题确实是环境的、时序依赖的或外部的：

1. 你已完成流程
2. 记录你调查了什么
3. 实施合适处理（重试、超时、错误消息）
4. 为将来调查加监控/日志

**但是：** 95% 的"无根因"案例都是调查不完整。

## 真实世界影响

来自调试会话：
- 系统化方法：15-30 分钟修复
- 随机修复：2-3 小时乱撞
- 首次修复率：95% vs 40%
- 引入新 bug：接近零 vs 常见
