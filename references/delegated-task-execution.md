# 子代理驱动开发

## 加载时机

在当前会话中执行带独立任务的实施计划时加载。它是 `plan-execution.md` 的替代方案（后者使用独立的并行会话）。

## 核心原则

每个任务派一个新子代理，配合任务评审（规格 + 质量）与最终整分支评审，得到高质量与快速迭代。子代理只接收精心构造的上下文，**绝不接收会话历史**；你的上下文因此保留给协调工作。

## 选择依据

| 条件 | 选择 |
|---|---|
| 有实施计划 + 任务基本独立 + 留在本会话 | 本方法 |
| 有计划 + 可接受并行会话 | `plan-execution.md` |
| 无计划或任务紧耦合 | 先做规划，或手工执行 |

## 执行流程

```
读计划 → 对每个任务：
    派发实施子代理
    实施者有疑问？→ 回答后重新派发
    实施者汇报状态
    生成评审包，派发任务评审
    评审者：规格 ✅ 且质量通过？
        否 → 派发修复子代理 → 复审
        是 → 标记任务完成，追加台账
全部任务完成后：
    派发最终整分支评审
    使用 branch-integration.md
```

任务之间不停顿检查，连续执行到全部完成。只在以下情况停下：你无法解决的 BLOCKED、阻碍进展的歧义、或所有任务完成。

## 开工前的计划扫描

任务 1 开始前，通读计划找冲突：
- 任务之间互相矛盾，或与计划 Global Constraints 冲突
- 计划显式要求、而评审标准视为缺陷的内容（如不断言的测试、逻辑块逐字重复）

以一次批量提问把发现连同对应计划文本呈现给用户，问以哪个为准，再开始执行。扫描干净则静默继续。

## 模型选择

派发时总是显式指定模型。省略会继承你的会话模型——通常最贵——从而悄悄破坏本节意图。

| 任务类型 | 模型档位 |
|---|---|
| 机械实施（1-2 个文件、规格完整） | 最便宜 |
| 多文件集成、模式匹配 | 标准 |
| 架构与设计判断 | 最贵 |
| 最终整分支评审 | 最贵（而非会话默认） |
| 任务评审 | 中档或更高（评审需要判断力） |

轮次数比 token 价格更影响总成本：最便宜模型在多步工作上常多花 2-3 倍轮次。评审者与从散文工作的实施者以中档为下限；计划内含完整代码（转写 + 测试）时用最便宜档即可。

## 实施者状态处理

| 状态 | 动作 |
|---|---|
| DONE | 生成评审包，派发任务评审 |
| DONE_WITH_CONCERNS | 阅读顾虑：正确性或范围类先解决再评审；观察类记录后继续 |
| NEEDS_CONTEXT | 补足缺失上下文后重新派发 |
| BLOCKED | 上下文问题→补信息同模型重试；需要推理→换更强模型；任务过大→拆分；计划错误→上报用户 |

绝不忽略升级，也不在无实质变化时让同一模型反复重试。

## 评审者 ⚠️ 项处理

任务评审可能报 "⚠️ Cannot verify from diff"（需求位于未改代码或跨任务）。它不阻塞其余评审，但标记任务完成前必须逐项解决：你掌握评审者缺少的计划与跨任务上下文。确认为真实缺口时按规格评审失败处理——退回实施者并复审。

## 构造评审者提示的规则

- 没有具体的任务内理由，不加开放式指令（如 "check all uses"、"run race tests if useful"）
- 不要求评审者重跑实施者已跑过的测试
- 不预判结论（"do not flag"、"don't treat X as a defect"、"at most Minor"、"the plan chose"）；让评审者自行提出发现，在评审循环中裁决
- 全局约束块是评审者的注意焦点：从计划逐字复制约束性需求（精确值、格式、组件间关系）；流程规则（YAGNI、测试卫生）已在评审模板中
- 以文件形式提供 diff：运行本 skill 目录下的 `scripts/review-package BASE HEAD`，传入打印出的路径；diff 不进你的上下文。BASE 用派发实施者前记录的提交，绝不用 `HEAD~1`（会截断多提交任务）
- 一次派发只描述一个任务，不粘贴累积摘要；新子代理需要：它的任务、它触碰的接口、全局约束
- Critical 与 Important 发现派发修复子代理；Minor 记入进度台账，让最终评审指向该清单——无人阅读的汇总等于丢弃
- 标为 plan-mandated 的发现由用户裁决：呈现发现与计划文本，问以哪个为准；不擅自驳回也不擅自违背计划
- 最终整分支评审：`scripts/review-package MERGE_BASE HEAD`（MERGE_BASE = `git merge-base main HEAD`），传入打印路径
- 每次修复派发附带实施者契约：修复子代理重跑覆盖测试并报告，点名覆盖测试文件；复审前确认报告包含覆盖测试、运行命令与输出
- 最终评审有发现时，用一个带完整清单的修复子代理，不要按发现逐个派发——逐个派发会各自重建上下文并重跑套件，成本超过全部任务之和

## 文件交接

粘贴进派发提示的内容与子代理打印回的内容都会驻留你的上下文，因此工件一律用文件传递。

| 工件 | 机制 |
|---|---|
| 任务简报 | `scripts/task-brief PLAN_FILE N`——把任务全文抽到唯一命名文件并打印路径 |
| 实施者报告 | 实施者返回的文件；按简报命名（`task-N-brief.md` → `task-N-report.md`） |
| 评审者输入 | 三个路径：brief、report、review package + 全局约束 |
| 修复派发 | 修复报告（含测试结果）追加到同一报告文件；复审读更新后的文件 |

实施者派发应包含：① 一行说明任务在项目中的位置；② 简报路径，说明"先读它——它是你的需求，含需逐字使用的精确值"；③ 简报无法知道的、来自前置任务的接口与决策；④ 你对简报中歧义的裁决；⑤ 报告文件路径与报告契约。精确值（数字、魔数、签名、测试用例）只出现在简报中。

## 持久进度台账

对话记忆无法跨压缩存活；丢失位置的控制器曾重新派发整段已完成任务，这是观察到的最高成本失败。

- 启动时检查台账：`cat "$(git rev-parse --show-toplevel)/.analyze/sdd/progress.md"`。标记 complete 的任务不再派发；从第一个未完成的任务恢复。
- 任务评审干净后追加：`Task N: complete (commits <base7>..<head7>, review clean)`。
- 台账是你的恢复地图：压缩之后信任台账与 `git log`，而不是自己的记忆。
- `git clean -fdx` 会删除台账（git-ignored 草稿），可从 `git log` 恢复。

## 红线

绝不：
- 未经用户明确同意在 main/master 上开始实施
- 跳过任务评审，或接受缺任一结论的报告（规格与质量都必须）
- 带未修复的 Critical/Important 问题继续
- 并行派发多个实施子代理（会冲突）
- 让子代理读整个计划文件——只给任务简报
- 省略场景设定上下文
- 忽略子代理提出的问题
- 接受规格合规的"差不多"
- 跳过评审循环
- 让实施者自审替代真实评审
- 指示评审者不要标什么，或在派发中预评严重度
- 没有 diff 文件就派发任务评审
- 评审有未决 Critical/Important 问题时进入下一任务
- 重新派发台账已标记 complete 的任务
