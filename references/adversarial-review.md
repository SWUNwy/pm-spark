# S-AR 对抗性审查手册（Adversarial Review）

> 分析综合完成后、方案输出前触发；本手册定义审查触发位、角色配置、问题处置与 review-log 工件。审查不增加 PM 工作模式、交互深度或交付等级。

## 1. 触发与职责

在方案或分析结果准备交付前进行；它是内部质量检查，不新增 PM 工作模式、阶段、交付等级或权限选择。检查对象是方案本身的完整性、边界和关键假设，不替代产品内容、交付契约或真实对话验收。

## 2. 审查视角

由负责挑战需求的内部审查视角组织，按当前问题需要参考用户、系统或业务视角。视角用于发现问题，不要求 PM 选择角色，也不改变当前交付类型。

| 分析类型 | 辅助角色 |
|---------|---------|
| 需求分析 | User Advocate |
| 方案设计 | System Architect |
| 战略分析 | Product Strategist |
| 混合 | 按主导类型选择，至多 2 个 |

Risk Challenger 负责组织审查、汇总发现、判定严重级别；辅助角色只在其视角内提出发现，不参与定级。

## 3. 审查维度

- **完整性**：参考 Intake Audit 六维度（背景与问题/目标与价值/用户与场景/功能边界/成功指标/约束与依赖），只检查会改变当前结论、范围、风险或交付类型的缺口；不要求六维度全部有答案。非关键缺口标为假设或待验证，不阻断当前交付。
- **边界**：按当前请求检查异常流、降级路径、空态、并发/重复操作、恶意或意外输入对核心流程的影响；不要求所有场景一律展开。
- **假设证据**：关键假设是否有用户事实、已查验本地或外部证据支撑？区分事实、推理与待验证假设，不把无证据的假设写成事实。

## 4. 发现与处置

每条发现记录 `id`、`severity: blocking | advisory`、`claim`、`persona` 和 `resolution`。这两个处置严重性仅供内部审查使用，不是 PM 可选等级。

- **blocking**：未解决会使当前结论不可靠或核心流程不可用，例如决定性假设无依据、关键产品边界遗漏、既有规则冲突。
- **advisory**：只影响后续优化或非关键细节，明确记录，不阻断当前交付。

内部发现状态沿用 `Open / Resolved / Waived`。可依已有事实修复时先自行修订；只有需要不可替代的用户判断时才转 `awaiting_user`，每轮最多问一个会改变当前结果的关键问题。风险接受须有用户明确决定及原因，记录适用范围与残余风险，不把豁免写成已修复。无法解决的问题标为待确认或受阻，不能宣称已就绪。

模式二的目标是给出假设及后果、挑战问题和「推进 / 先验证 [X] 再决定 / 推回去」之一。证据不足可以支持「先验证」裁定，不阻断挑战结论的输出；挑战问题清单供 PM 带去讨论，不要求用户当轮逐项回答。

用户可见消息只说明产品缺口、影响与交付状态，不播报门禁编号、角色名、机器状态或严重性枚举：

> 当前交付待确认：[产品缺口] 会影响 [结论/范围/风险]。请确认：[一个关键问题，可附选项]？

## 5. 审查记录与交付边界

模式一、二仅在对话交付，不自动写审查文件。4C 固定交付 `proposal.md` + `design.md` + `tasks.md`，内部审查记录不得自动增加用户交付文件。需要内部留痕时在已有 run 的 evidence / check 中记录发现与处置；独立 `review-log.md` 仅在用户明确要求时生成，写文件前展示路径并确认。

PM 评审正文使用产品工作语言；内部 `id / severity / persona / claim / resolution` 留在机器工件中。用户明确要求调试时再解释必要细节。可按下列产品模板记录真实发现，不预填已解决或已豁免的结论：

```markdown
# 方案审查记录

- **审查对象**：[当前方案/分析主题]
- **审查日期**：[实际日期]

| 产品问题 | 对当前结果的影响 | 依据或待验证假设 | 处置与残余风险 |
|----------|------------------|------------------|----------------|
| [实际发现] | [具体影响] | [真实证据引用或明确假设] | [已修订内容/待确认项/用户风险接受及范围] |

## 交付状态

[草稿 / 待确认 / 已就绪 / 受阻]：[已完成检查与尚缺内容]
```

## 6. 交互深度

轻量 / 标准 / 深度只影响依据、比较与核验投入；任何深度都检查影响当前结果的关键假设与边界，不因轻量而跳过或取消阻断。信息够用即停，不为填满审查清单追问；结果之后最多一个可选下一步，用户要求结束时不再追问。不自动扩展到方案设计、PRD、Spec 或实现。

## 7. 恢复与验收

- 已有 run 的 state、evidence / check 是恢复依据；核对实际产物与证据，从未完成的关键项继续，不把旧通过标记当作当前证据。
- `review-log.md` 仅是用户明确请求的评审工件，不是权威恢复源；缺少证据时标为待确认或受阻，不宣称已就绪。
- 审查通过不授予实施或外部动作权限；具体动作遵循宿主策略及用户已有授权。
- 静态契约检查与本手册审查均不能证明真实对话通过。真实行为验收按 `references/pm-behavior-acceptance.md` 单独运行，未运行保持 `not_run`；不得虚构对话、证据或通过状态。
