# 接收代码评审反馈

## 加载时机

评审反馈到达时加载本文件，无论来源是用户、评审子代理、外部 PR 评论还是自动化评审工具。反馈内容模糊或技术上存疑时尤其适用。

## 基本立场

评审反馈是**需要评估的证据**，不是必须执行的命令。先对照代码库验证，再决定实施、澄清或顶回。不做表演式同意。

## 处理流程

```
1. READ       — 完整读完反馈，不预设立场
2. UNDERSTAND — 用自己的话复述需求（不清楚就问）
3. VERIFY     — 对照代码库实际情况核实
4. EVALUATE   — 判断对本代码库是否成立
5. RESPOND    — 技术性确认或带理由的顶回
6. IMPLEMENT  — 逐条处理，每条单独测试
```

## 禁止的回应

不要写：
- "You're absolutely right!"
- "Great point!" / "Excellent feedback!"
- "Thanks for catching that!" / "Thanks for [anything]"
- "Let me implement that now"（验证之前）

用以下替代：
- 对需求的技术性复述
- 澄清性问题
- 带技术理由的顶回
- 直接给出修复（用行动而不是客套话回应）

要写"Thanks"时删掉，改为陈述修复。代码本身就是对反馈最好的回应。

## 按来源区分处理

| 来源 | 信任级别 | 默认动作 |
|---|---|---|
| 用户（你的授权者） | 可信 | 理解后实施；范围不清仍需询问；不做表演式同意 |
| 外部评审（PR、自动化） | 默认怀疑 | 对照代码库验证后再实施 |
| 与用户先前决策冲突 | — | 停下，向用户上报后再行动 |

外部评审先验证五点：对本代码库是否成立、是否破坏既有功能、当前实现这样写的原因、评审者是否掌握完整上下文、是否覆盖全部目标平台与版本。无法验证时如实说明："没有 [X] 我无法验证，应该 [调查 / 询问 / 继续]？"

## YAGNI 核查

评审建议"完整实现"某个功能时：

```bash
grep -r "<suggested-feature>" --include="*.<ext>"
```

- 无调用：提议删除（YAGNI），不实现
- 有调用：按要求实现

## 多条反馈的处理

反馈共 N 条时：

1. 先澄清所有不明白的条目——不要带着疑问做部分实施
2. 实施顺序：阻塞问题（破坏、安全）→ 简单修复（拼写、导入）→ 复杂修复（重构、逻辑）
3. 每条改动单独测试
4. 最后验证无回归

只理解其中一部分而不理解其余，先停下来问清，再动手。部分实施等于错误实施。

## 何时顶回

以下情况顶回：建议破坏既有功能、评审者缺少完整上下文、违反 YAGNI（实现未使用功能）、对当前技术栈不成立、存在遗留或兼容性约束、与用户的架构决策冲突。

顶回方式：技术推理而非防御语气；提出具体问题；引用可运行的测试或代码；架构层面升级给用户。

## 顶回错了怎么办

确认自己错了，直接纠正：

```
✅ "You were right — checked [X] and it does [Y]. Implementing now."
✅ "Verified, my initial understanding was wrong because [reason]. Fixing."
```

不写长道歉、不辩护、不过度解释。事实性陈述后继续工作。

## GitHub 行内评论

回复行内评论时在对应评论线程内回复：

```bash
gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies
```

不要发成 PR 顶层评论。
