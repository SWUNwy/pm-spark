# 测试驱动开发（TDD）

## 加载时机

进入 `execute` 阶段（见 `plan-execution.md`）并开始写任何生产代码之前，先加载本文件。在 `verify` 阶段或 `debugging-discipline.md` 流程中修复 bug 时同样适用。

## 核心契约

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

规则没有例外：先写代码再补测试，等于测试后置，不是 TDD。已经写在测试之前的代码，删除并重来；"留作参考"同样是事后测试。契约的字面与精神必须同时遵守。

需要先与用户确认的例外：一次性原型、自动生成代码、纯配置文件。

## 循环：Red → Green → Refactor

| 阶段 | 要做什么 | 必须验证 |
|---|---|---|
| RED | 为一个行为写一个最小测试 | 测试失败（而非报错），且因预期原因失败（功能缺失，不是拼写或导入问题） |
| GREEN | 写通过该测试的最小代码 | 测试通过；其他测试无回归；输出干净 |
| REFACTOR | 改进命名、去重、抽取辅助函数 | 全部测试保持通过；不引入新行为 |

跳过 RED 的失败验证，测试可能因错误原因通过或根本没测到目标行为。"稍后再验证失败"就是跳过。首次运行就通过，说明测试在测既有行为或什么都没测——修测试，不要进入 GREEN。测试报错而不是失败，先修报错原因，重跑到干净地失败为止。

## 何时必须 TDD

| 场景 | 是否 TDD | 说明 |
|---|---|---|
| 新功能 | 必须 | |
| 修复 bug | 必须 | 先写能复现 bug 的失败测试 |
| 重构 | 必须 | 测试在改动前锁定现有行为 |
| 一次性原型 | 询问用户 | 默认仍走 TDD |
| 生成代码 | 询问用户 | |
| 配置文件 | 跳过 | |

"就这一次跳过"是合理化借口，不是例外。出现这种念头时回到本表。

## 完成门禁：TDD-Complete

宣称一个工作单元完成前，逐项确认：

- [ ] 每个新函数或方法都有对应测试
- [ ] 每个测试都曾在实现之前观察过失败
- [ ] 每次失败的原因都符合预期
- [ ] 每项实现都是通过该测试的最小代码
- [ ] 全部测试通过
- [ ] 输出无警告、无错误
- [ ] 测试作用于真实代码；mock 仅在不可避免时使用
- [ ] 边界情况与错误路径有覆盖

任一项不满足，说明 TDD 被跳过——从头再来。

## 识别合理化借口

出现以下想法时停下，回到 TDD：

| 想法 | 事实 |
|---|---|
| "简单到不用测" | 简单代码同样会坏，写测试只要几十秒 |
| "之后补测试" | 事后测试会立即通过，证明不了任何行为 |
| "事后测试效果一样" | 事后测试回答"这段代码做了什么"；先行测试回答"这段代码应该做什么" |
| "手动测过就行" | 临时验证不可复现、无记录 |
| "已经花了 X 小时，删掉可惜" | 沉没成本；未验证代码是负债 |
| "留作参考，先写测试" | 你必然还会改它，那仍是事后测试 |
| "先探索一下" | 可以，但探索产物要扔掉，再用 TDD 重写 |
| "测试难写 = 设计有问题" | 难测通常意味着难用，听测试的 |
| "TDD 拖慢进度" | 事后调试更慢 |
| "TDD 太教条，我要务实" | TDD 本身就是务实——提交前发现 bug |
| "这次情况不一样" | 不，没有例外 |

## 修复 bug 的接入方式

执行或验证中发现 bug：

1. 写一个能复现该 bug 的失败测试
2. 运行 RED 验证，确认失败原因正确
3. 走 Red-Green-Refactor 循环
4. 该测试同时证明修复有效并防止回归

没有回归测试，不修 bug。

## 测试质量要求

| 维度 | 合格 | 不合格 |
|---|---|---|
| 最小化 | 一个测试只测一个行为；名字含 "and" 就拆分 | `test('validates email and domain and whitespace')` |
| 清晰 | 名字描述行为 | `test('test1')` |
| 真实 | 用真实代码；万不得已才 mock | 断言 mock 交互而非代码行为 |

卡住时的排查方向：

| 现象 | 可能原因 |
|---|---|
| 不知如何写测试 | 先写想要的 API 再写断言；设计本身不清楚 |
| 测试过于复杂 | 设计过于复杂，简化接口 |
| 必须 mock 一切 | 耦合过强，改用依赖注入 |
| setup 代码庞大 | 抽取辅助；仍复杂则简化设计 |

## Mock 使用红线

- 不测 mock 行为本身，只测真实行为
- 不给生产类添加仅供测试使用的方法
- 不理解依赖的真实契约就不要 mock
