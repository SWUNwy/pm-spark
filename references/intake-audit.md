# Intake Audit（需求摄入检查清单）

本清单用于模式一「理解问题」中的按需检查。六个维度帮助识别会影响当前工作的缺口，但不是前置门槛、完整性问卷或必须逐项填满的表格。

## 使用原则

- 先判断当前请求要交付什么：问题陈述、判断、方案方向、PRD、原型注释或其他明确结果。
- 只检查与当前结论、范围、风险或交付类型有关的维度。其余维度可以暂留空，并在输出中标注为假设或待验证。
- 只有当缺口会改变当前结论、范围、风险判断或交付类型时才追问。
- 每轮只问一个问题，优先问最能改变当前结果的那一项；问题应尽量提供可选回答。
- 如果已有信息足以支持当前结果，立即停止澄清并交付，不为了凑齐六个维度继续追问。
- 信息不足但不影响当前结果时，带着明确假设继续；信息不足且会改变结果时，指出影响并提出一个问题。

## 六个检查维度

| 维度 | 检查什么 | 什么时候值得追问 |
|------|---------|------------------|
| **背景与问题** | 发生了什么，为什么现在处理 | 不清楚问题对象会改变问题陈述或判断 |
| **目标与价值** | 想改善什么，谁从中受益 | 不清楚目标会改变推荐方向或交付类型 |
| **用户与场景** | 谁在什么情境下遇到问题 | 不同用户/场景会导致范围、方案或风险明显不同 |
| **功能边界** | 做什么、不做什么，覆盖到哪里 | 缺口会导致交付范围无法判断或容易越界 |
| **成功指标** | 用什么信号判断是否有效 | 当前任务需要比较、决策或可观察验收时，缺口会改变结论 |
| **约束与依赖** | 技术、法务、排期、系统或组织限制 | 缺口会改变可行性、风险路径或交付类型 |

## 按需检查步骤

1. 识别当前要交付的结果和已经可以确认的事实。
2. 快速扫过六个维度，只标记会影响当前结果的缺口；不要逐项向用户索取状态。
3. 若没有影响结果的缺口，直接输出当前结论或交付物，并说明必要的假设。
4. 若存在影响结果的缺口，只选择影响最大的一个问题询问。
5. 用户回答后，重新判断剩余缺口；若结果已经稳定就停止，若仍有一个缺口会改变结果，再进入下一轮。

## 追问判断表

| 缺口影响 | 处理 |
|---------|------|
| 会改变当前结论 | 追问；回答后更新结论 |
| 会改变范围或非目标 | 追问；先锁定影响最大的边界 |
| 会改变风险或安全路径 | 追问；说明缺口会带来的风险差异 |
| 会改变交付类型 | 追问；确认用户要问题陈述、方案、PRD、注释或其他交付 |
| 只影响细节、格式或后续优化 | 不阻断当前工作，作为假设/待验证项记录 |
| 对当前结果没有影响 | 跳过，不提问 |

## 提问格式

每轮只保留一个需要用户回答的问题：

> 为了确认当前的[结论/范围/风险/交付类型]，我只需要知道：**[一个具体问题]**？

可在问题后给出 2–3 个选项，但不要把多个维度合并成一组问题。得到足够信息后，直接进入当前请求的交付，不自动扩展到其他模式或文档。

## 输出记录

需要留痕时，记录实际检查过的维度、影响当前结果的缺口、提出的问题及回答摘要。没有影响当前结果的维度无需列出，也无需声明“已完成六维度审计”。推荐使用：

```markdown
### 当前判断
- 结论：[当前可交付的结论或结果]
- 依据：[用户已提供的事实]
- 假设/待验证：[只列会影响后续的少量事项]
- 澄清状态：信息已足够 / 等待一个关键回答
```

## 示例

### 信息已经足够

输入：客服每天手动归类投诉，目标是减少整理时间；当前只需要理解问题并给出下一步。

处理：背景、目标、用户场景已有足够落点。即使成功指标和技术约束尚未确定，也不改变当前问题陈述，因此直接输出问题陈述，并把指标列为后续验证项。不追问剩余维度。

### 缺少一个会改变结论的关键项

输入：想减少投诉漏处理，但还不清楚是客服本人漏看，还是系统没有提醒。

处理：只问一个问题：“目前主要是哪一种情况：客服没有看到待办，还是系统没有产生提醒？”根据回答再决定问题陈述和下一步；不同时询问目标、指标、边界和约束。

### 缺口不影响当前交付类型

输入：方案方向已选定，只要求整理产品需求文档；接口实现方式和排期尚未确定。

处理：交付类型、产品范围和用户可见规则足够支持 PRD 草稿。接口与排期留作后续协作项，不为了补齐它们而暂停或改成技术 Spec。
