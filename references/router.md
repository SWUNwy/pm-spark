# PM Spark 路由（Router）

当前用户入口以 `SKILL.md` 的五种 PM 工作模式为准：理解问题 / 挑战需求 / 设计方案 / 规格化与交付 / 做决策。下文轨道、成熟度与门禁只用于内部兼容和状态恢复，不要求 PM 选择，也不作为用户可见入口；按当前请求够用即停，不自动串联全部模式。

## 1. 分类顺序

按此顺序路由：

1. 用户显式的目标与排除项。
2. 授权与风险。
3. 任务成熟度与当前 run 状态。
4. 主导认知轨道。
5. 推荐深度与证据负担。

## 2. 轨道选择

| 信号 | 轨道 | 默认行为 |
|---|---|---|
| 模糊想法、重新定义、可能性空间 | Explore | 扩展维度与假设 |
| 需求、决策、方案、战略、权衡 | Analyze | 定义标准、比较、推荐 |
| 正式需求、验收、任务、交接 | Specify | 运行就绪与冻结门禁 |
| 直接实施请求 | Handoff | 不作为第四个分析轨道 |

信号混杂时，按请求的交付物在内部选择兼容轨道。其他轨道只作为简短子步骤，不要造成可见的模式切换噪音。

## 3. 风险与证据负担

| 风险 | 示例 | 证据/批准行为 |
|---|---|---|
| 低 | 可逆探索 | 用标注假设继续 |
| 中 | 干系人影响、有意义成本 | 检查可用来源；暴露置信度与一个验证动作 |
| 高 | 不可逆、法律、医疗、财务、安全、声誉 | 验证易变事实、比较备选方案、要求人工承诺 |

风险提高验证负担，不自动增加提问。只有当缺失答案会改变安全路径时才问。

## 4. 成熟度

| 等级 | 信号 | 动作 |
|---|---|---|
| M0 | 碎片、顾虑、情绪 | 复述并提供 2-3 种解读；仅在缺口会改变下一步时问一个问题 |
| M1 | 有方向无结果 | 提出目标契约与一个决定性提问；已有信息足够时直接形成当前结果 |
| M2 | 有选项/冲突 | 归类分支并定义标准；只追问会改变推荐的缺口 |
| M3 | 目标与约束清晰 | 进入所选轨道并验证；不因其他维度未填写而延迟 |

成熟度只帮助决定当前需要的工作深度，不要求先完成一套完整摄入检查。

## 5. 拆解（Decomposition）

请求包含可独立交付的系统、受众或决策时，在深度分析前拆解。设 `decomposition_required=true`，创建 Decomposition Map，选择一个垂直切片（带自己的结果与验收证据），在 state 中保留延后切片，并在 `scoped` 前通过 G-Decompose。不要浅层分析全部分片。

## 6. 反锚定协议（Anti-anchor）

重大建议时：

1. 标注哪些事实来自当前请求、先前对话、已查验来源与假设。
2. 不使用先前推荐，重构选项集。
3. 先定义决策标准，再给选项打分。
4. 自问：推荐路径是全局最优，还是只是最容易延续？
5. 说明什么新证据会推翻该决策。

仅在有助于用户审计依据时使用 `Reset`、`Continue` 或 `Mixed` 标签。

## 7. 外部事实

- 任务授权只读工作时，查验本地/项目事实。
- 用可用来源验证易变或与用户关联的事实。
- 无法验证时，提供条件分析并精确标注未验证声明。
- 宿主策略已允许时，普通只读验证不需要请求许可。
- 传输数据、创建副作用或实质扩大范围前先询问。

## 8. 兼容映射

| v1 | v2 |
|---|---|
| Brainstorming | Explore 轨道 |
| Analysis | Analyze 轨道 |
| Spec | Specify 轨道 + G-Spec Freeze |
| Execution | 下游宿主交接 + 宿主批准 |
| 对话中的会话状态 | 可用时的机器可读 run 状态 |
| Stage Summary | 已验证检查点 |
